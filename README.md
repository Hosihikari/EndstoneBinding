# Hosihikari.Bindings.Endstone

The **Endstone** C++ interop surface for the Hosihikari projection: a CI-generated native-style **Interop** and the native **binding shim**.

## Boundary

- `Hosihikari.Bindings.Endstone.Interop` is generated by `Hosihikari/BindingGenerator` from the versioned IR. It mirrors Endstone declarations: single-level pointer and reference returns become typed borrowed wrappers, `optional_ref<T>` results reuse those wrappers, and other opaque handles stay `nint`. ABI value types and the shim loader come from `Hosihikari/BindingAbi`.
- `native/BindingShim/` is the C ABI projection. Endstone plugins resolve the server through `endstone::detail::getServer()`; the shim uses the same bootstrap and calls virtual interfaces directly, so it needs no Endstone import library.
- The shim builds on Windows x64 with clang-cl. On Linux x64, CI builds the libTooling frontend, generates `linux-x64-server` IR from the Endstone headers, emits the same Interop surface from that IR, and compiles the shim with `native/BindingShim/build.sh`.
- The hand-written Idiomatic layer is deferred; the generated Interop is the current public interop surface.

## Current state

- Interop: 217 generated C# files under `src/Hosihikari.Bindings.Endstone.Interop/Generated/`.
- 绑定垫片: 2,364 functions in `native/BindingShim/generated/win-x64-server/endstone/`.
- Coverage: 319 declarations and 1,831 members bound.

The shim is emitted in `--virtual-dispatch` mode. Inline members, virtual methods (including pure virtual interfaces), eligible template instances, inline/constexpr static fields, `std::optional<T>` parameters/results, `std::vector<T>` parameters/results, `std::unique_ptr<T>` results, `std::shared_ptr<T>` results, `nonstd::expected_lite::expected<T, std::string>` results, `std::variant<T...>` parameters/results, `NotNull`/`Nullable` shared handles, borrowed pointer sets, owned/shared element arrays, chrono time values, returned `std::function` callables, `unordered_map` parameters and results as dictionaries, `shared_ptr` parameters as shared handles, `unique_ptr` parameters as ownership transfers, and borrowed-string identifiers through holder-backed factories, namespace-level inline functions as `Functions` static classes, and `ModalForm` controls through the typed form-control variant are projected; non-virtual out-of-line members remain Interop stubs with a reasoned `NotSupportedException` message and an `[Obsolete]` marker that raises CS0618 when called. Host-owned interface objects are not disposed; only objects created by the shim receive a disposer.

`NativeMethods.Load(path)` loads the shim. `NativeMethods.GetServer()` returns the host `endstone::Server` handle, which can be wrapped with the generated `Server` class.

## Generate

The frontend parses `include/endstone/endstone.hpp` with the Endstone dependency headers:

```shell
powershell -File ../Binding.Generator/frontend/run-endstone.ps1
powershell -File scripts/regenerate.ps1 -IrDirectory ..\Binding.Generator\artifacts\endstone-ir -AbiRoot ..\Binding.Abi
```

## Build

```shell
dotnet build Hosihikari.Bindings.Endstone.slnx -c Release
powershell -File native/BindingShim/build.ps1
```

The generated shim directory contains `hosihikari_abi.h` from `BindingAbi`, so the native build stays self-contained. The native build uses clang-cl, C++20, the MSVC STL, and the expected-lite/nlohmann_json headers already provisioned by the local toolchain. It does not link `endstone_core`; calls dispatch through the host-provided virtual interfaces.

## Benchmarks

`scripts/run-benchmarks.ps1` loads the shim in a real Endstone server through a native plugin that hosts the CLR with `nethost`/`hostfxr`, then runs the managed benchmark assembly in-process. It reports nanoseconds and managed allocation per call for scalar and string methods, string/int vector parameters, map parameters and results, variant-valued maps, and shared handles. Results are written to `data/hosihikari/shim-benchmarks/benchmarks.txt`; the numbers are environment-dependent and are not a CI gate. See `tests/benchmarks/README.md`.

## Generated-source gate

`scripts/verify_generated.py` checks provenance, the coverage baseline, the native table function count, the table version, and the managed table. CI builds the solution, runs the verifier, and validates the committed coverage contract with the generator.
